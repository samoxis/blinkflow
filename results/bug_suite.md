## Mutations without a contact in 20 s (not in the set)

- stop distance too short: `[obstacle] stop_distance = 0.12`
- sensor offset sign inverted: `hazards._detect: lateral = d*by - sensor_lateral`
- side points dropped beside the body: `hazards.update: side points kept only while fwd >= 0.0 (was -0.15)`
- ahead columns too narrow: `[obstacle] front_first_col = 3, front_last_col = 5`
- clear distance too small: `[obstacle] clear_distance = 0.29`
- steering starts too late: `[obstacle] slow_distance = 0.36`
- sensor sides swapped: `depth.analyse: left half = columns 4-7, right half = columns 0-3`
Why the seven did not touch anything in 20 s: the brain has three layers between the robot and an obstacle: the wall view from the upper rows, the low-object layer from the bottom rows, and a side memory that keeps wall returns near the body for 3 s and merges them into the corridor. Mutations of the front decision (stop 0.12, columns 3-5, clear 0.29) leave the side memory to catch the box as it passes along the legs, so the robot still walks past it. A sweep of about 100 variants earlier in the day found a contact for those only with the side layer switched off (for example stop 0.16 with columns 2-4 gives a head contact at about 11 s). The inverted sensor offset moves side returns by 2 × 0.0224 m, which is small compared with the 0.30 m band. With `fwd >= 0.0`, side points still last until the sensor is level with the box, which is just enough for the legs. Slow 0.36 and the swapped halves gave no contact even with the side layer off: they change where the robot turns, not whether it stops. b13 was valid but not kept, because the set takes the first six.

## Where it went wrong, and why

- **All six bugs are the same failure, written six ways.** Every kept mutation disables or starves the side memory. The contact is always the right leg (ankle or upper leg) on the same box at 11.5-12.4 s. The 20-s filter selected for this one route to a collision, because the side layer masks everything else. So 6/6 says BlinkFlow fixes broken side memory reliably. It does not say BlinkFlow fixes any bug. A broader set needs a scene where the side layer cannot help, such as an object that is never at the edge of the view.
- **b3: right area, wrong line, and a partial fix.** Two of the three Wonder runs put the cause in `hazards._detect` and named the constant and its value (0.12). The definition, however, lives on line 31, outside the cited range, so the line metric counts it as a miss. The third Wonder run and all three Spark runs blamed the near-sensor mask in `depth.analyse`. Muse Code raised `SIDE_LOOKAHEAD` to 0.30 instead of restoring 0.8. That passes this scene, but it is a shorter side memory than the original, and no other scene has tested it. Attempt 1 was a reasonable patch (`max(SIDE_LOOKAHEAD, stop_distance)`). It was rejected by our own audit: the token `*/brain.toml` in a shell command was read as the absolute path `/brain.toml`, outside the target. That was a false positive, and it was fixed before b4. So b3 ran under a stricter, buggy audit than the other five.
- **b4: the right diagnosis, and a patch that brings back the trace the injector avoided.** Wonder found `side_memory_seconds = 0.05` in `brain.toml`. Muse Code set it to 5.0, not 3.0, and left `config.py`'s default at 0.05. The scene passes because `brain.toml` wins. Anyone running the brain without that file gets the bug back, and the config and the default disagree again.
- **Spark is the weaker diagnostician here.** Across the six first diagnoses, 14/18 Wonder runs and 12/18 Spark runs cited a mutated line. The gap is concentrated in b9, where Wonder scored 3/3 and Spark 1/3, with Spark blaming `depth.py`. Muse Code receives Wonder's majority, which is why the comparison matters.
- **The run was not one clean pass.** Two harness fixes landed during the suite. The audit fix came before b4. The API-error check was too loose: it matched an earlier "ended" line, restarted b3, and discarded its first run. The SAM daily cap ($5) stopped the suite at b9 before any loop call. Following the instruction not to stop for cost, b9-b10 were rerun with `BLINKFLOW_SAM_BUDGET=12 BLINKFLOW_WONDER_BUDGET=30` set for the suite only; the defaults in code stay $5/$15. The day's ledgers, including everything before the suite and the discarded b3 run, end at SAM $6.52 and Muse Wonder $6.78. That is above the $3/$6 the suite was first given.
- **One rendering bug surfaced in the report.** Wonder's em dashes arrived as `â\x80\x94`: `requests` decodes a `text/event-stream` with no charset as latin-1. `blinkflow/models.py` now forces UTF-8 on the stream. The one affected character in the b7 row was repaired by hand.

## What the layered suite shows

- **Control.** The repaired brain stayed clean in all five scenes for 20 s, so every scene stayed in. Two of them, corner and doorway, are still control-only: none of their own layer's mutations produced an incident there. Stop distance 0.12/0.16, the freer side inverted, and the corridor at 0.04/0.05 m all gave the same result, with the duck meandering and never touching anything. The stop decision is made twice, once in the wall view and once again when side memory is merged back in, so weakening one layer leaves the other still holding. A stuck robot is not counted, because in the box the clean brain already lingers for about 10 s. A blocking detector would mostly be detecting patience. That is why the corridor layer's bug comes from the box scene.
- **Four layers, two failures.** Low objects (3) and side memory (1) were fixed on all three measures. The drops layer (b5, b6, b7) failed on 2 of 3. In b6 and b7, Muse Wonder named `depth.py::low_obstacles`, which is the wrong layer. Muse Code's notes describe the ledge as "a shallow tray" or "rim", so the evidence of a fall was read as a low object. The three attempts kept changing the low-object filter, and the robot fell at 10.25 s every time. b5, where the position of the drop was swapped, was fixed: there, Wonder went straight to `drop_zones`.
- **Attempt 2 was rejected before replay in both b6 and b7 in the first run.** The approval guard caught them. In b6, Muse Code wrote `/tmp/tray_probe.py`, a correct rejection. In b7, the guard read the arithmetic `/1000.0` in a bash command as a path outside the target. That false positive is now fixed: a path must start where a shell word can, so `x[i]/1000.0` is a division. In the rerun, b7's attempt 1 was again rejected correctly, this time for writing `/tmp/probe_low.py`.
- **Wonder ran out of room on the ledge.** The first run of b6 and b7 each ended with 12000 reasoning tokens and no answer. `diagnose.py` crashed on a missing key instead of failing as an API error. It now keeps only runs that have a diagnosis, and the limit is now 32000 output tokens. Each bug was rerun once, counted as "+1 after API error".
- **The ledge still beats the loop, even with the history.** A retry's diagnosis now receives every earlier cause, its change, and what the replay showed, including whether the first contact moved at all. In the rerun, Wonder saw that attempt 1 left the contact at exactly 9.32 s. In attempt 3 of both b6 and b7 it switched to another place, `hazards.py::update` (confirmation of hazards across detection gaps), but never to the drop layer (`drop_zones` and the `[drop]` settings). Glimmer names the ledge "yellow tray", and that word reaches Wonder and Muse Code unchanged: everyone looks for an object to step around, nobody for an edge to fall off. b6 and b7 remain not fixed, and they stay in the report as failures.
- **b10 was a measurement miss, now fixed.** With the corridor at 0.05 m, the twin logs the jaw touching `demo_box` at 18.43 s. In the first run, `see.py` counted only contacts at the base (feet at the box's depth), so the replay before any change showed no contact and the loop stopped before Muse Code. `see.py` now has a second reading, used only when the base sees nothing: the masks touch while the robot's lowest point is within 0.65 of its own on-screen height of the base. Re-measured from the saved SAM replies at no cost, it reads b10 at 18.35 s and 18.385 s and changes no other run. One reading cannot simply replace the other: in the box scene a leg passes through that band 0.8 s before it reaches the base. In the rerun, the loop saw the contact, Wonder named `hazards.py`, and Muse Code widened the corridor for side hazards in code, so the incident is gone and the control is clean. (c) still counts 0/2, because the mutated value in `brain.toml` was left alone.
- **(c) is weaker than (a).** b2 and b9 were fixed with no regressions, but Wonder pointed at the code and not at the configured value. Muse Code's change reaches the mutated lines without restoring their value: the incident went away by another route.
- **Cost.** $20.12 in model calls in total: $12.94 for the eight loops of the first run, plus $7.18 for the rerun of b6, b7 and b10 (SAM 3.1 $8.87, Muse Wonder $7.99 overall). The suite ran with `BLINKFLOW_SAM_BUDGET=25 BLINKFLOW_WONDER_BUDGET=30` from the environment. The code defaults are still $5 and $15.
